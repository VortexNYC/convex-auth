title: Migrating from Clerk
description: Concept mapping and the import path from Clerk to convex-auth.
---

Moving from Clerk to convex-auth means your users, sessions, organizations, and UI all move into your Convex deployment — there is no hosted middle tier left. The component ships `migrate:*` writer mutations plus a `normalizeClerkExport` normalizer (`@vortex-api/convex-auth/migrations`) that maps Clerk API and dashboard-CSV exports onto them; `scripts/migration-e2e/` in the repo is a working driver that seeds, pulls, normalizes, and applies against a scratch deployment.

## Concept mapping

| Clerk                             | convex-auth                                                                                                                                 |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `<ClerkProvider>`                 | `ConvexAuthClientProvider` — see the [React guide](./react)                                                                                 |
| `<SignIn />` / `<SignUp />`       | `ConvexAuthSignInPage` / `ConvexAuthSignUpPage` — [UI components](./components)                                                             |
| `useAuth()` / `useUser()`         | `useSession()` / `useConvexAuthUser(authClient)` — [React guide](./react)                                                                   |
| `auth()` in `middleware.ts`       | Next.js adapter middleware — [Next.js guide](./nextjs)                                                                                      |
| Organizations, memberships, roles | [Organizations](./organizations) — first-class tables, roles, invitations                                                                   |
| `<OrganizationSwitcher />`        | `ConvexOrganizationSwitcher` — [UI components](./components)                                                                                |
| Sessions list / "Devices"         | `ConvexSessionList` — [UI components](./components)                                                                                         |
| Webhooks (user.created, …)        | [Webhooks](./webhooks) — signed lifecycle events                                                                                            |
| Backend API keys                  | None — Clerk secret keys are Clerk's own API credentials. The convex-auth [API keys](./api-keys) feature issues keys _for your_ API instead |
| JWT templates                     | Native Convex JWTs — see [Architecture](./architecture)                                                                                     |

## The cutover path

1. **Stand up convex-auth** alongside Clerk: mount the component, wire `convex/auth.ts`, and point a staging app at it. Follow the [Quickstart](./quickstart).
2. **Export users from Clerk** — the Backend API (`GET /v1/users`, `/organizations`, `/organizations/{id}/memberships`, `/organizations/{id}/invitations`) for users and org structure, plus **Settings → User Exports → Export all users** in the dashboard for the CSV that carries password digests.
3. **Import users.** Feed the API JSON plus the dashboard CSV into `normalizeClerkExport` — it handles banned/locked filtering, `org:` role-prefix stripping, slug-collision skips, and turns pending organization invitations into invited seats. Apply the result with the component's `migrate:migrateUser` / `migrateAccount` / `migrateOrganization` / `migrateMembership` mutations (the e2e driver calls them over authenticated HTTPS via `/api/function` with a deploy key, falling back to `convex run --component`). Banned users and their memberships are skipped; any role that doesn't already exist in the destination org — including imported `admin` — lands with **empty permissions**, never `*`, until you grant scopes.
4. **Passwords carry over.** The dashboard CSV's `password_digest` column holds real `$2a$`/`$2b$`/`$2y$` bcrypt hashes — convex-auth verifies them (cost 4–14) and lazily rewrites each credential to native argon2id on the user's first successful sign-in. Users whose rows lack a digest land on the reset path instead — they set a password via [forgot password](./email-password) before first sign-in.
5. **Recreate organizations.** The same importer writes orgs and memberships, preserving role keys — `org:admin` and `org:member` strip the `org:` prefix to `admin` / `member`. Neither exists in a fresh destination org (which seeds only `owner` + `member`), so `admin` — like any custom key — is created as an org-local role with **no permissions** until you grant scopes. Source-system admin powers do not carry over.
6. **Cut the client over** route by route — Clerk middleware off, the adapter's middleware on. Old Clerk session tokens die with the provider, so plan a single sign-out event.

## What does not migrate

- Active sessions — every user signs in once more.
- Clerk TOTP secrets and passkeys — users re-enroll (migrated users land with 2FA off, so nobody is locked out).
- Clerk's hosted UI session handling, device tracking granularity, and enterprise SSO connections — SSO providers become [Generic OAuth](./generic-oauth) configs.
